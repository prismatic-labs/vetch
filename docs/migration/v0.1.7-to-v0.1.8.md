# Migration Guide: v0.1.7 → v0.1.8

## Overview

Version 0.1.8 introduces Schema v2 with multimodal support and critical security fixes. This guide helps you migrate from v0.1.7 to v0.1.8.

**Breaking Changes:** None - all changes are additive and backward compatible.

**Security Improvements:**
- Tag redaction now uses HMAC-SHA256 (16-char output vs 8-char)
- Tag processing order fixed to prevent PII leakage
- SSRF protection enhanced with DNS rebinding prevention
- Tag cardinality rate limiting added (100 new values/hour per key)

---

## Schema v2 Changes

### Usage Field Restructuring

**Schema v1 (v0.1.7 and earlier):**
```python
{
  "usage": {
    "input_tokens": 100,
    "output_tokens": 50,
    "total_tokens": 150
  }
}
```

**Schema v2 (v0.1.8):**
```python
{
  "usage": {
    "text": {
      "input_tokens": 100,
      "output_tokens": 50,
      "total_tokens": 150
    },
    "image": None,
    "audio": None
  }
}
```

### New Fields in Schema v2

| Field | Type | Description |
|-------|------|-------------|
| `multimodal` | `bool` | True if request uses non-text modalities |
| `estimated_water_l` | `float \| None` | Water usage in liters (datacenter cooling) |
| `embodied_carbon_g` | `float \| None` | Hardware manufacturing emissions |
| `tracking_degraded` | `bool` | True if tracking accuracy is reduced |
| `trace_id` | `str \| None` | W3C trace ID for APM correlation |
| `span_id` | `str \| None` | W3C span ID for APM correlation |
| `parent_span_id` | `str \| None` | Parent span ID for nested operations |
| `is_batch` | `bool` | True if using batch API (future) |
| `is_embedding` | `bool` | True if embedding generation (future) |
| `grid_intensity_time_of_day` | `bool` | True if using hourly grid data (future) |

## Code Migration

### Option 1: Use Compatibility Helper (Recommended)

If you're consuming Vetch events and need to support both v1 and v2:

```python
from vetch.schema import normalize_usage_v1_to_v2

# Your existing event processing code
event = get_vetch_event()  # May be v1 or v2

# Normalize to v2 format
event = normalize_usage_v1_to_v2(event)

# Now safe to access nested usage structure
text_usage = event["usage"]["text"]
if text_usage:
    tokens = text_usage["input_tokens"]
```

### Option 2: Update Your Code to Handle Both Formats

```python
def get_input_tokens(event):
    usage = event.get("usage")
    if not usage:
        return 0

    # v2 format (nested)
    if "text" in usage:
        text = usage.get("text")
        return text.get("input_tokens", 0) if text else 0

    # v1 format (flat)
    return usage.get("input_tokens", 0)
```

## Grafana Dashboard Updates

If you have existing Grafana dashboards querying Vetch events, update your queries to handle the new nested usage structure.

### Example: Total Tokens Panel

**Before (v0.1.7):**
```jsonnet
{
  "expr": "sum(vetch_usage_total_tokens)",
  "legendFormat": "Total Tokens"
}
```

**After (v0.1.8):**
```jsonnet
{
  "expr": "sum(vetch_usage_text_total_tokens)",
  "legendFormat": "Text Tokens"
}
```

If you're using OTLP export with custom metric names, ensure your Prometheus/Grafana queries account for the new structure.

## OTLP Filter Changes

If you're filtering OTLP events by schema version:

**Filter for v2 events only:**
```
schema_version="2"
```

**Filter for events with multimodal content:**
```
schema_version="2" AND multimodal=true
```

**Filter for high-quality tracking (not degraded):**
```
tracking_degraded=false
```

## Security Configuration Changes

### Tag Redaction Hash Length

Redacted tag values now use 16-character hashes instead of 8:

**Before (v0.1.7):**
```
user_email: "redacted-a1b2c3d4"
```

**After (v0.1.8):**
```
user_email: "redacted-a1b2c3d4e5f6g7h8"
```

**Impact:** If you have scripts parsing redacted values, update regex patterns:
```python
# Before
pattern = r"redacted-[a-f0-9]{8}"

# After
pattern = r"redacted-[a-f0-9]{16}"
```

### HMAC Key Configuration

Set `VETCH_REDACTION_KEY` for deterministic hashing across environments:

```bash
export VETCH_REDACTION_KEY="your-secret-key-here"
```

Without this, hashes are based on hostname (stable within a machine but differ across deployments).

### Tag Cardinality Rate Limiting

New rate limits prevent DoS attacks:
- **Per-key limit:** 100 new unique values per hour
- **Global limit:** 10,000 total tracked values (LRU eviction)

**Impact:** If your application submits more than 100 new tag values per key per hour, you'll see warnings in logs. Consider:
1. Reducing tag value cardinality (e.g., group user IDs into cohorts)
2. Using allowlist filtering to exclude high-cardinality tags

## Testing Your Migration

### 1. Verify Schema v2 Events

```python
import vetch

with vetch.wrap(region="us-east-1", tags={"team": "platform"}) as ctx:
    # Your LLM call
    response = client.chat.completions.create(...)

# Check schema version
assert ctx.event["schema_version"] == "2"

# Verify nested usage structure
assert "text" in ctx.event["usage"]
```

### 2. Test Backward Compatibility

```python
from vetch.schema import normalize_usage_v1_to_v2

# Simulate v1 event
event_v1 = {
    "schema_version": "1",
    "usage": {"input_tokens": 100, "output_tokens": 50, "total_tokens": 150}
}

# Normalize to v2
event_v2 = normalize_usage_v1_to_v2(event_v1)

# Verify conversion
assert event_v2["usage"]["text"]["input_tokens"] == 100
assert event_v2["usage"]["image"] is None
```

### 3. Test Tag Redaction

```python
import vetch

vetch.set_redacted_tags(["user_email"])
vetch.set_tag_allowlist(["team", "user_email"])

with vetch.wrap(tags={"team": "platform", "user_email": "alice@example.com"}) as ctx:
    # Your LLM call
    pass

# Verify redaction (16-char hash)
user_email_value = ctx.event["tags"]["user_email"]
assert user_email_value.startswith("redacted-")
assert len(user_email_value) == len("redacted-") + 16
```

## Rollback Plan

If you need to rollback to v0.1.7:

1. **Downgrade package:**
   ```bash
   pip install vetch==0.1.7
   ```

2. **No data migration needed** - v0.1.7 events are compatible with v0.1.8 consumers (using `normalize_usage_v1_to_v2` helper).

3. **Restore tag redaction key** (if you were using custom HMAC key):
   ```bash
   unset VETCH_REDACTION_KEY
   ```

## Common Issues

### Issue: "Tag 'X' exceeds hourly rate limit"

**Cause:** Your application submits >100 new unique values for a tag key within 1 hour.

**Solution:**
1. Reduce tag cardinality (e.g., use `user_cohort` instead of `user_id`)
2. Increase limit (not recommended for security):
   ```python
   # Not exposed yet in v0.1.8, deferred to v0.2.0
   ```

### Issue: Grafana panels show no data after upgrade

**Cause:** Metric names changed due to nested usage structure.

**Solution:** Update Grafana queries from `vetch_usage_total_tokens` to `vetch_usage_text_total_tokens`.

### Issue: HMAC hashes differ across deployments

**Cause:** Default HMAC key is based on hostname.

**Solution:** Set `VETCH_REDACTION_KEY` to a consistent value across all environments.
